# Automations

When, and as whom, an agent runs.

**This folder ships patterns, not instances.** Automation files are the one layer that never ports between repos — every ticket key, label string, host path and cron inside them belongs to the repo that wrote them. A copied automation still pointing at another project's epic will happily file your tickets there.

So you derive yours here, from these conventions, for your tracker and your host. Nothing to scrub, because nothing was inherited.

Sibling layers: [`../skills.md`](../skills.md) defines *how* the work is done. [`../guardrails/`](../guardrails/) defines what an agent may never do. Automations wire the *when*.

## The shape

One markdown file per agent. Frontmatter for the machine-readable parts, body for the instructions. Instructions reference **skills** for the actual work — automations never restate a skill's content.

```markdown
---
name: triage-agent
description: Moves untriaged tickets to agent-ready briefs.
model: sonnet          # a capability tier, never a vendor model id
layer: worker
triggers:
  - on: "webhook(tracker: issue created, or label needs-triage added)"
skills:
  - triage
tools:
  - gh
guardrails:
  - Tracker-only — never modifies code.
  - One workflow label at a time; replace, don't accumulate.
  - Sign every comment: *This was generated by the `triage-agent` automation.*
---

You are the `triage-agent` automation.

**Scope**: the ticket named in the fire's payload. If no ticket key is in your
context, the rule is misconfigured — exit silently. Never hunt for work.

If the ticket has already been triaged since entering this state, exit silently.

Then run the `triage` skill on exactly that ticket, using the vocabulary in
`docs/agents/triage-labels.md` and `docs/agents/issue-tracker.md`.
```

That's the whole format. The body is prose an agent reads, not config.

## Three layers

Events ring workers. Joiners decide.

- **Workers** (`layer: worker`) do one work item per fire — one ticket, or one PR × one review lens. Tracker-side workers are rung by webhooks naming their ticket. PR-side workers are fired by PR events and work the triggering PR.
- **Joiners** (`layer: joiner`) fire often and act rarely. Each run checks whether its join condition holds — all review lenses reported, a human verdict exists — and only then routes. **A joiner run that doesn't act posts nothing.**
- **Standalone** (`layer: standalone`) crons are self-contained single units of work.

There's no dispatch layer and no sweep cap. The platform's triggers do the fan-out that cron sweepers used to.

## The rules

Each one was learned by breaking it.

**One writer per label edge.** And the writer is the *definition file*, not a trigger registration. Three registrations of one definition are still one writer. Write the ownership down:

- `triage-agent` owns the edges out of `needs-triage`.
- `implementer` owns `ready-for-agent` → `agent-review`, for its own ticket.
- `review-verdict` owns everything out of `agent-review`.
- `human-verdict` owns everything out of `human-review`.
- Reviewers never touch labels.

**Automations never merge.** Their credentials must not carry merge rights. This is the load-bearing rule — everything else here is decoration without it.

**Every automation signs its output.** Every comment starts with *"This was generated by the `<name>` automation."* It's how humans and agents tell authors apart when they share one account, and it's how comment-triggered joiners recognise their own and each other's comments and stay silent on them.

**The ticket is the ledger.** Every automation comments its activity there — the implementer's PR link, each reviewer's verdict, the joiners' transitions — so the ticket alone tells the whole story and links ticket ↔ PR. Disable per-automation platform memory, or treat it as non-authoritative.

**Triggers carry no filters on most platforms.** So every event-triggered automation's first step is a prompt-level bail-out: exit silently unless this work item is actually in scope. These bail-outs are load-bearing, not defensive.

**Reviewers use independent lenses and never touch labels.** One definition per lens, and a joiner decides when they've converged. Never let a reviewer read another reviewer's findings — the independence *is* the value.

**Keep the flow diagram in sync** in the same commit as any trigger or label-edge change. A stale diagram is worse than none.

## Trigger vocabulary

Described by meaning. The setup contract maps them to whatever the platform calls them.

- `on: pr-opened` — a pull request was opened.
- `on: pr-pushed` — new commits landed on an open PR's branch.
- `on: pr-approved` — a human approved.
- `on: pr-merged` — merged.
- `on: pr-comment` — a top-level comment was added.
- `on: webhook(tracker: <rule>)` — the tracker rings a private webhook endpoint. `<rule>` describes the tracker-side condition by meaning; the rule itself lives in the tracker's automation config, documented in `docs/agents/issue-tracker.md`.
- `schedule: "<cron>"` — plain cron, standalone only.

## Scoped fires

Every webhook fire names its work item. The tracker rule sends the issue key; the worker takes that as its scope.

**A fire with no key in context means a misconfigured rule.** The worker exits silently rather than hunting for work.

One event, one run, one item — no claim protocol. Duplicate fires are rare: a manual label re-application, or an undocumented platform retry. Each worker's cheap ledger check absorbs the common cases — *has this state already been handled since the ticket entered it? does my verdict for this sha exist?* Anything that slips through is visible, harmless by guardrails, and cleaned up by hand.

## No janitor

There is deliberately **no cron backstop** re-sweeping for stuck tickets.

The consequence is accepted: a dropped event strands its ticket in-state until a human notices. The rescue is manual — re-add the label to re-fire, push to the PR branch, or run the worker by hand with an explicit scope.

If drops turn out to be common, the answer is a **detector**, not a sweeper: a scheduled agent whose deterministic pre-check finds items sitting in a state too long, and whose agent only spends tokens diagnosing the ones that are. A sweeper needs a claim protocol and duplicates work.

## Runtime contract

Every agent boots from the same line:

> You are the `<name>` automation. Read `.agents/automations/<name>.md` and follow it. [Scope: `<ticket / PR + lens>`]

The scope suffix is optional — webhook workers take the ticket named in the fire, PR-event automations take the triggering PR. It stays the way a manual run pins an explicit scope.

Everything else lives in the automation's file.

## Setup contract

> Set up the automations defined in `.agents/automations/` on &lt;platform&gt;.

Provision the environment first — see [`../environments/`](../environments/) and the `/provision-automation-environment` skill. Stock environments generally can't reach a private repo.

Registration is **out-of-repo state on every platform tried so far**: dashboard entries, webhook URLs, bearer keys, tracker rules. Mechanical to reproduce from this folder, drift-prone in practice.

After any dashboard edit, bring this folder back in sync in the same breath.

Map the frontmatter to the platform's own names:

| This vocabulary | Typically |
| --- | --- |
| `pr-opened` / `pr-pushed` | Pull request opened / pushed |
| `pr-approved` / `pr-merged` | Pull request approved / merged |
| `pr-comment` | Comment added |
| `webhook(...)` | Webhook — save to mint a URL + bearer key, then pair it with the tracker rule |
| `schedule` | Scheduled |
| `model: haiku \| sonnet \| opus \| fable` | the platform's mapping of that tier |

## Platform findings

Undocumented behaviour, found the hard way. Update as you verify.

**Cursor**
- **No automations API and no in-repo file format.** Registration is dashboard-only; "automations as code" is an open feature request.
- The Cloud Agents API **accepts GitHub repos only** — no programmatic spawning against a GitLab repo.
- PR triggers have **no filters** (author, label, branch). Prompt-level bail-outs are load-bearing.
- **Webhook payload → prompt visibility is undocumented.** Assume the body reaches the agent, and have workers exit silently without a key. Verify on the first live fire.
- Event delivery and dedup semantics are undocumented. Absorb duplicates with ledger checks.
- GitLab **inline-discussion comments do not fire** "Comment added". The human fast path is a top-level comment or an approval.
- GitLab integration requires **Premium/Ultimate**. Hard prerequisite.
- Nested-group repo pickers load partial lists for large orgs. Workaround: Integrations → sync repositories, then search the full path.
- Per-automation `MEMORIES.md` persists outside the working tree, **on by default**. Disable it. The ticket is the ledger.

**Claude routines**
- Hourly crons fire at a **platform-assigned minute** (the routine's creation minute). Requested minutes are rewritten and updates ignored. Don't let correctness depend on a stagger.
- Git sources must be `https://<host>/<owner>/<repo>`. **Nested group paths are rejected** — work around with a token-clone setup script.
- **"Trusted" network mode blocks non-allowlisted git hosts** (503/DNS failure). Externally-hosted repos need full network access.
- **Environment-dialog variables are not injected into setup-script execution.** Parameterize the setup script with `export` lines prepended to the pasted copy.
- The trigger API can't read session output — human-readable only. `run` works on disabled triggers.
- No native spawn tool in the sandbox. Fan-out is in-session workflow waves; inline serial as fallback.
- A project access token acts as a bot user, so host comments are visibly bot-authored. Tracker comments may still act as the connector's human account — the signature rule covers that gap.

## Deterministic scripts

Before adding a script here, ask: **does any step need judgment?**

- **No, fully deterministic** → it isn't an automation. It's cron or CI. Put it in `scripts/` and wire it into the pipeline. Don't spend an agent on it.
- **Yes, but one step is deterministic** → put the script inside the skill that uses it, and have the automation invoke the skill. A cheap deterministic pre-check gating the agent — *run X; if clean, stop* — lives fine in the automation body.
- **Automation-specific, neither reusable skill nor standalone CI** → the escape hatch is a directory form: `<name>/` holding the `.md` plus `scripts/`, mirroring skills. Don't create the form until one actually needs it.

## Conventions

- One file per automation, kebab-case, `name` matches the filename.
- **Keep the flow diagram in sync** — any add, remove, rename, trigger or label-edge change updates it in the same commit.
- `triggers` use the vocabulary above, always by meaning, never a platform's UI label.
- `model` names a **capability tier** (`haiku` < `sonnet` < `opus` < `fable`), not a vendor model id. The platform maps it. Judgment-heavy work — implementation, bug and structure review — gets the strongest tier. Joins and checklists don't.
- `tools` name capabilities (`gh`, `glab`, tracker MCP), not platform connector IDs.
- Repo context — tracker conventions, label vocabulary — is referenced from `docs/agents/`, never duplicated here.
